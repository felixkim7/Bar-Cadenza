  - After all runs: 0 leftover python processes from the project .venv.
  - The real−sim difference (~17–33 ms) is the final frame's limiter wait after the last advance, as expected.
- Findings:
  - pygame-ce SCALED sets the window minimum size to the logical size (1280×720). Smaller requests are clamped. Risk for small or high-DPI laptop screens → revisit at T009/T043 (O007).
  - Under SCALED, `pygame.Window.size` changes from code are ignored, and `Window.from_display_module` is deprecated. Stress mode resizes through Win32 SetWindowPos, which emits the same WINDOWRESIZED/WINDOWSIZECHANGED events as a user drag.
  - SCALED scales a 1280×720 surface, so text will soften at larger window sizes. Text-crispness strategy belongs to T003/T009.
- Manual Windows checks and results (user, native Windows, 2026-11-26, `uv run python -m bar_cadenza.app.window_experiment`):
  1. Holding a window-edge drag ~3 s: the square freezes during the drag and "dropped" increases afterward. Expected SDL2 behavior: Windows runs a modal move/resize loop that blocks the app loop, so the post-drag gap exceeds the 1 s cap. Loop resumes normally on release.
  2. Maximize/restore: works.
  3. Held key, typing, fast mouse movement: the square keeps moving.
  4. Close with X: the window closes and the terminal returns.
- Remaining limitations / decisions: during an active window drag/resize, rendering and the loop stall (SDL2 on Windows; no clean fix in pygame-ce 2.x). Whether sim time catches up or drops that stall is part of O008 (T007); currently gaps > 1 s are dropped. The gap-cap value and focus/suspend behavior stay provisional under O008 (T007).
