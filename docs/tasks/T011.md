- Behavior:
  - **One file per game.** Each new game is its own SQLite file, `save-<UTC time>-<id>.sqlite3`, in the per-user saves folder. A damaged or newer save is never overwritten by another game, and a new file is created exclusively, so an existing one is never reused.
  - **Schema:**
    - `saves` holds save_id, language (CHECK ko/en), content_version and created/updated times;
    - `progress` holds the shift (CHECK ≥ 1);
    - both are STRICT tables, and foreign keys are on;
    - the version lives in `PRAGMA user_version`, and migrations are append-only. Older saves are upgraded inside the load's transaction, so a failed upgrade rolls back.
  - **Transactions:** create, load and write are each one transaction. A failure rolls back and raises `SaveError(reason)` (`unreadable`, `newer` or `failed`), naming the file.
    - A save that can't be read, or comes from a newer version, is never modified.
    - A failed create removes only its own half-made file.
    - Opening a save never creates a file.
  - **Allowlisted fields:** only language and shift (plus IDs and times) are written, as typed columns. Nothing is pickled, so no objects, threads, futures or keys can be stored.
  - **In the game:**
    - choosing a language creates the save;
    - closing for the night saves the next shift, so reloading after "Main menu" starts that next shift;
    - Continue loads the newest file by modification time.
    - Each save shows "Progress saved." or a failure message. The game goes on with its progress in memory and never claims a save that failed.
